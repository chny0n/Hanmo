# 한모 학사자료 가공·보존·정리 운영 체크리스트

> **설계 정본:** [docs/architecture.md §7.1](architecture.md)의 데이터 경계·수명주기 계약. 이 문서는 운영자용 절차이며, 설계를 독립적으로 변경하거나 학교의 자료 이용 허가를 대신하지 않습니다.
>
> **현황:** 현재 Supabase 실데이터 반입·DB 보존 자동화는 미구현. [학교 자료 사용권 #27](https://github.com/ot4562-glitch/Hanmo_develop/issues/27) 확인 전에는 수집·재배포·운영 공개하지 않습니다.

## 1. 자료 등급과 보존 정책

**보존 시계:** 최근 3개 학년도는 당해 학년도와 앞선 2개 학년도(정규·계절학기 포함)를 뜻합니다. 90일은 **확인된 마지막 유효 종료·대체·취소일**부터 계산합니다. 종료 시점·분류·권리 조건이 불명확하면 자동 삭제 대상이 아니라 검수 보류입니다. 과거 이력이 필요한 복합 공지는 **규정 영향 → 반복 행사 → 단순 안내** 순으로 분류하고, 단순 공지의 상세 내용만 시한부로 정리합니다.

## 2. 가공 계약

1. **권리 사전 검사:** 자료 유형별 원문 열람·자동 수집·요약/구조화 저장·재배포 허용 범위를 개별 확인합니다. UNKNOWN/LIMITED/DENIED/REVOKED는 확인된 권한을 넘는 수집·저장·공개를 차단합니다. 학교 인증 우회나 자동 대량 추출을 하지 않습니다.
2. **원문 식별·변경 감지:** 공식 식별자, URL, SHA-256, 관측/게시/정정 시각, sourceRevisionId를 기록합니다. PDF/HTML/첨부 및 학생 원장은 서버에 통째로 저장하지 않습니다.
3. **정규화·중복 제거:** 과목 ID와 학기·캠퍼스별 개설, 분반 상세, 교수 표시명, 공지 ID/개정 ID, 학생 마감과 행정 마감, 행사 회차, RulePack 적용 조건을 분리합니다. 명칭 유사성만으로 같은 과목/공지로 확정하지 않습니다.
4. **출처 완전성:** 미관측·자료 누락·식별 불명은 UNKNOWN입니다. 정본 범위가 완전함을 확인하지 못한 학기에서 NOT_OFFERED를 생성하거나 미관측을 k/n의 분모에 넣지 않습니다. 관측된 분반 수는 전체 분반 수의 증명이 아닙니다.
5. **시점/검수 분리:** 원문 게시/관측 시점, 수집 시점, 검수·승인 시점, 적용 시점을 구분합니다. 추출 코어·AI 제안은 후보일 뿐, 서로 다른 실검수자/승인자와 권리 승인 뒤 공개합니다. 미래에 알게 된 정정 내용을 과거 전망의 입력에 소급 사용하지 않습니다.
6. **목적별 투영:** 현행 학생 검색에는 유효 공지·최근 시간표·현재 적용 RulePack만 공개하고, 전망에는 역사적 OFFERING_HISTORY·EVENT_HISTORY의 **필요한 행과 집계**만 사용합니다. 전체 학교 원장을 매 요청마다 반환하지 않습니다.

## 3. 오래된 자료 정리 절차 — 현재는 수동 승인 게이트

- 매월 분류·기한·철회 상태를 점검하고 매 학년도 전환 시 3개 학년도 경계를 다시 계산합니다.
- 현재/최근 분반의 보존기간이 끝나면 출처·관측 완전성·검증된 분반 수·과목/학기별 이력을 먼저 검증합니다. 이후 **teaching_assignments → sections** 순서의 상세 제거 계획을 작성합니다. 역사적 과목 개설 관측과 참조 중인 source_revisions는 삭제하지 않습니다.
- 일반 공지의 상세 후보는 정정/취소와 관련 RulePack/반복 행사 자료로 **필요한 역사 정보를 먼저 추출·검수**합니다. 실제로 지울 수 있는 내용과 남겨야 할 감사 증거를 분리합니다.
- 공개 스냅샷은 승인된 현행판 중심으로 크기를 제한합니다. 지난판 payload를 무한 복제하지 말고, 안전한 롤백 필요·철회 의무·독립 승인·백업을 확인한 뒤 별도 코드 리뷰를 거친 정리 기능을 적용합니다. **철회판본은 재활성화 금지**입니다.
- 어떤 DELETE/아카이브/인덱스 정리도 **운영자 사전 승인, 영향행 미리보기, 참조관계 검사, 검수된 최신판 보존, 수동 암호화 백업·복구 시험 및 사후 DB 용량 측정** 이전에는 실행하지 않습니다. 권리 철회 시 데이터 공개를 즉시 중지하는 것은 보존기간보다 우선합니다.

## 4. Supabase Free 용량·전송 점검

- Free DB의 공식 한도는 **500MB/프로젝트**이며 행·인덱스·시스템 점유를 포함합니다. **250MB 이하 운영 목표**, **300MB 예방 최적화**, **400MB 신규 대량 반입 보류**를 팀 내부 경계로 사용합니다.
- 월 비캐시/캐시 전송량은 각각 5GB 한도를 별도로 측정합니다. 대형 공개 JSON을 학생에게 매번 내려보내지 않고 캠퍼스·학기·검색 조건을 적용한 작은 응답을 우선합니다.
- 최초 승인 샘플에서 테이블별 건수와 pg_total_relation_size, DB 전체 pg_database_size, 대표 공개 응답 바이트 수, 학생 조회 패턴을 실측합니다. **2010년 이후 전체 커버리지나 동시 이용자 규모는 실측 전 보장하지 않습니다.**
- 매월 예상 성장량·보존 등급별 용량을 재평가합니다. 신규 임계치 도달 시 유료 전환 대신 반입/대량 요청 중단, 검수된 정적 대체 또는 확인 필요 상태로 전환합니다.
