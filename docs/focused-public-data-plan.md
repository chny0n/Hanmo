# 공지·일정 비교 기능과 최소 데이터 운영 계획

> **설계 결정 · 2026-11-23.** 현재 수집 범위에서 우선 개발할 기능과 필요한 데이터의 상한을 정합니다. 기능 구현·실자료 검수·수집 활성화·Supabase 설치 완료를 뜻하지 않습니다. 현행 제품·기술 정본은 [아키텍처](architecture.md), 자료 이용 기준은 [잠정 운영 방침](public-data-operating-decision.md)입니다.

## 1. 우선 기능: 공지·일정 비교

기존 **학사 공지 검색과 학사 달력을 연결**합니다. 검색 결과에서 같은 행사에 관한 공지를 묶고, 새 정정 공지와 이전 공지의 차이 및 출처별 일정 불일치를 비교합니다. 검수된 날짜만 달력에 표시합니다. 학생이 여러 게시판을 다시 읽거나 정정 전 일정을 최신 일정으로 착각하는 일을 줄이는 것이 목적입니다.

| 후보 | 효용과 제약 | 결정 |
|---|---|---|
| 공개 강의 개설 관측·전망 | 수강 계획에 유용할 수 있으나 ‘수강 관련 정보’의 금지 경계가 불명확하고 과거 자료·충분한 관측이 없음 | #48에서 별도 검수. 이 기능의 수집 범위에 포함하지 않음 |
| 공식 문의처 정밀 탐색 | 적은 데이터로 문의 경로를 줄일 수 있으나 부서·업무·연락 경로의 검증이 필요 | #59의 보조 기능으로 유지 |
| 공지 메타데이터 고급 검색 | 제목·게시일·분류·원문 링크로 구현할 수 있고 현재 화면을 직접 개선 | 비교 기능의 기반으로 채택 |
| **공지·일정 비교** | **작은 메타데이터로 정정·중복·출처 불일치를 함께 확인하고 기존 달력을 활용** | **1순위 기능으로 채택** |

이 순위는 현재 정책·데이터·구현 상태에 따른 제품 판단입니다. 실제 이용자 실험으로 효과가 입증된 순위는 아닙니다. 개인 메모·알림, 장문 AI 요약, 학생별 신청 자격·마감·졸업 판정은 핵심 범위에 넣지 않습니다.

### 사용자 흐름

**게시판 1개 단계에서는 같은 게시판의 신규 정정·중복 후보 비교와 검수된 날짜의 달력 연결**을 제공합니다. 다른 게시판의 출처 비교는 두 번째 출처의 검수를 마친 뒤 확장하며, 처음부터 여러 게시판을 포괄한다고 표현하지 않습니다.

1. `academic-timeline.html`에서 검색어·캠퍼스·분야·기간과 `전체 / 변경 있음`으로 찾습니다. 기본 기간은 최근 30일입니다.
2. 결과 행에는 제목·게시일·검수된 행사 날짜·출처를 표시합니다. 비교할 내용이 있을 때만 관련 공지와 변경 영역을 펼칩니다.
3. **게시일·한모 관측일·행사 날짜를 구분**합니다. 제목이 비슷하다는 이유로 같은 행사나 정정본으로 확정하지 않습니다.
4. 검수된 정정 관계는 허용 필드의 이전 값과 새 값, 근거 공지를 나란히 보여 줍니다. 서로 다른 출처의 날짜가 충돌하면 양쪽 근거와 `확인 필요`를 표시합니다.
5. `academic-calendar.html`은 같은 이벤트 모델을 사용합니다. 날짜가 검수된 항목만 배치하고, 충돌·미확정 항목은 비교 목록에 남깁니다. 날짜가 없는 공지에서 임의 마감일을 생성하지 않습니다.
6. 최종 확인은 학교 원문으로 연결합니다. ‘전체 학교 공지’, ‘실시간’, ‘모든 변경 탐지’라는 표현을 사용하지 않습니다.

## 2. 적용할 정책과 실제 구현 상태

**직원 이메일과 대면 설명은 모두 학교 기관의 확정된 공식 입장이 아닙니다.** 내부 개발·운영 기준은 정했지만 학교의 포괄 승인이나 영구 사용권을 얻은 것으로 표현하지 않습니다. 향후 범위 확대·축소가 가능하며 `scopePolicyVersion`과 근거·검수·철회 기록을 연결합니다. 새 근거가 없으면 현행 명시 금지와 수집 제한을 유지합니다.

현재는 `data/academic-source-config.json`의 **`mode: disabled`**, 실제 학교 크롤러·공개 데이터·Supabase 연결 없음 상태입니다. 공지 화면에는 제목 검색 코드가 있으나 자료 미연결로 비활성화되어 있고, 달력은 FullCalendar의 빈 일정으로 동작합니다. 이 문서의 예산·보존·비교·자동 차단은 **구현할 계약**입니다.

연결 전에는 `js/academic-data-source.js`의 구형 `instructor`·`payload.faq` 계약을 폐기하고, 허용 필드만 받는 **DTO v2**를 설계해야 합니다. `docs/references/hufs-academic-source-candidates.json`의 과거 규정·시간표 후보는 이번 기능의 승인된 출처 목록이 아닙니다.

## 3. 기능에 필요한 최소 필드

| 영역 | 허용 후보 필드 | 목적 |
|---|---|---|
| 공지 | 내부 ID, 검수된 제목, 게시일, 캠퍼스, 분야, 출처 ID·공식 URL, 관측 시각 | 검색·필터·원문 이동 |
| 일정 | 내부 ID, 관련 공지 ID, 검수된 행사명, 시작/종료 날짜와 정밀도, 캠퍼스, 출처 URL | 달력·일정 비교 |
| 관계 | 연결 대상 ID, 정정/중복 후보 등 관계 종류, 확인 상태, 검수 ID | 공지 묶음과 정정 근거 |
| 변경 | 변경된 허용 필드명, 이전 값·새 값, 근거 공지 ID, 관측 시각 | 차이 표시 |
| 운영 | 정책판본, 출처 상태, 공개판본, 검수·철회 기록, 요청 장부 | 제한 준수·판본·중단 |

**제외:** 본문 전문·HTML·PDF·첨부·이미지, 교수명·학생명·개인 연락처·학적·성적·개인 수강내역, 정원·신청 현황·불명확한 분반/수강 정보, 학칙·졸업요건의 원문/링크/요약/판정, 개인별 자격·마감 추론, 본문 임베딩·벡터, 방문자별 계정·조회 기록입니다.

금지 정보는 제목에도 들어갈 수 있으므로 **필드 이름과 내용 모두 검수**합니다. 혼입 항목은 보류하고 원문을 오류 로그에 남기지 않습니다. 필요한 신규 상세는 메모리에서 필요한 메타데이터만 추출하며 원문은 저장하지 않습니다. 허용 여부가 불명확한 필드는 공개하지 않습니다.

## 4. 최소 수집 계약

학교 안내의 최대 50요청을 채우지 않습니다. 아래는 이 기능에 적용할 **더 작은 내부 상한**이며 목표 사용량이 아닙니다.

| 항목 | 내부 계약 |
|---|---|
| 출처 | 검수된 로그인 없는 공개 공지 게시판 **1개부터 시작**. 같은 기능에 추가 가치가 확인될 때만 **최대 2개** |
| 실행 | 전역 **하루 1회 이하**. 필요가 없으면 실행하지 않음 |
| 목록 | 출처별 **첫 목록 1개만**. 페이지네이션·검색 URL로 과거 목록 우회 금지 |
| 신규 상세 | 기능 범위·필드 검사를 통과한 **신규 공지 최대 10개/일**, 두 출처 합산 |
| 전체 HTTP | 출처 1개면 최대 11건, 2개면 최대 **12건/일**. 리다이렉트 등 추가 요청도 합산 |
| 간격·동시성 | 요청 시작 간격 **15초 이상**, 전역 동시 **1개**. 기존 최소 10초 조건보다 여유 확보 |
| 오류·접속 제한 | 첫 오류에 즉시 중단, **당일 재시도 없음**. 다른 러너·수동 실행·우회 경로로 재개 금지 |
| 수집 금지일 | 신청·정정 기간 전체와 시작 전/종료 후 각 1일. 전체 일정 미검증·장부 장애면 네트워크 접근 전 차단 |
| 식별·출처 | 공개 화면에 실제 노출된 URL만, 서비스명·운영자 연락처를 User-Agent에 표시 |
| 용량·권리 | 반입 여유·허용 필드·정책판본·철회 상태를 요청 전에 확인. 상한 또는 금지에 걸리면 중단 |

**첫 출처의 우선 검토 후보:** [한국외국어대학교 학사 공지 게시목록](https://dep.hufs.ac.kr/hufs/11282/subview.do). 근거는 [과거 커밋 `637f0d`의 공지 참고자료](https://github.com/ot4562-glitch/Hanmo_develop/blob/637f0d291a4bfb05bd91d640e3b25b8fa4b38b5a/degree-rescue/data/academic-notices-reference.json)의 **`REFERENCE_ONLY`** 출처 기록과 [현재 도메인 분류 시험](../js/academic/core/academic-display.test.js)에 남은 URL입니다. 둘 다 현재 접근 가능성이나 수집 승인의 증거가 아닙니다. **실접속·공개 화면에 노출된 경로·목록/상세 구조·필드가 미검수이므로 확정 수집 URL로 등록하지 않고 OFF를 유지**합니다. 과거 참고자료의 내용을 운영 데이터로 반입하지 않습니다.

### 첫 수집과 누락 처리

- **첫 실행도 과거 자료를 채우는 기회로 사용하지 않습니다.** 첫 목록의 출처·관측 시각·게시 범위·식별자를 초기 기준선으로 기록하고, 과거 상세를 따라가거나 기존 목록을 순회하지 않습니다.
- 이후 허용된 첫 목록에서 **신규 게시로 확인되는 후보 중 필요한 최대 10개만** 상세를 확인합니다. 초기 기준선의 기존 공지를 나중에 ‘신규’로 바꾸어 상세 수집하지 않습니다.
- 신규 후보가 상한을 넘거나 목록에서 사라지면 관측 누락을 기록합니다. **누락분을 후속 큐에 넣어 다음 날·다른 러너에서 돌려 받지 않습니다.** 저장하는 누락 기록도 출처·날짜·사유·건수 같은 최소 항목으로 제한합니다.
- 기간·출처·금지일·예산으로 생긴 누락을 `해당 없음`, `행사 없음`, `미개설`로 해석하지 않습니다. 화면에 관측 범위와 마지막 확인 시각을 제공합니다.
- 이 기능을 위해 **별도 시간표·달력 크롤러를 자동 추가하지 않습니다.** 첫 버전의 일정은 허용된 신규 공지에서 검수한 메타데이터를 재사용합니다. 별도 출처는 필요성과 수집 주기를 다시 검수하고 같은 전역 예산 내에서 결정합니다.

### 변경 탐지의 한계

**기존 상세를 매일 재조회하지 않습니다.** 비교 근거는 새 정정·취소 공지, 허용된 첫 목록에서 관측한 메타데이터 변화, 운영자가 별도로 제공해 검수한 새 근거로 제한합니다. 기존 상세 본문 안의 조용한 수정까지 모두 탐지할 수 없습니다. 날짜·정정 관계가 상충하면 임의로 최신값을 고르지 않고 공개 판단을 보류합니다.

새 정정 공지가 미관측 과거 공지를 참조하면 **‘이전 관측 없음’**으로 표시하고, 확보한 신규 메타데이터와 원문 링크만 제공합니다. 비교표를 채우기 위해 과거 상세를 백필하지 않습니다. **이전/이후 비교는 두 판본 모두 허용된 방식으로 관측하고 검수한 경우에만** 표시합니다.

## 5. 보존 기간과 행 수 상한

| 영역 | 초기 보존·건수 계약 |
|---|---|
| 공지 | 게시 후 **180일**, 최대 **2,000건** |
| 일정 | 과거 **30일**부터 미래 **180일**까지, 최대 **600건** |
| 비교 이력 | 항목당 과거 판본 **3개**와 **90일** 중 먼저 도달하는 경계 |
| 관계 | 최대 **4,000건** |
| 메타데이터 판본 전체 | 최대 **8,000건** |
| 검수·수집 장부·정책 | 초기 예산 합계 **6,000건**. 필요한 승인·철회 근거의 보존 조건을 함께 검수 |

보존 기간·행 수는 실제 운영량을 측정하기 전의 **초기 설계 예산**입니다. 행/바이트 상한에 닿으면 신규 반입을 멈춥니다. 승인된 보존 정책과 영향 미리보기에 따라 정리할 수 있는 것부터 정리하되, **검수 장부가 찼다고 승인 기록을 임의 삭제하거나 새 기록으로 덮어쓰지 않습니다.** 필요한 근거를 보존할 수 없다면 수집·발행을 중단하고 설계를 재검토합니다.

권리 철회에 따른 공개 중단은 보존 기간보다 우선합니다. 오래된 기록의 정리와 철회된 데이터의 재노출 방지는 별개의 작업입니다.

## 6. Supabase Free 예산

### 확인한 공식 한도

2026-11-23 확인한 [공식 가격표](https://supabase.com/pricing)는 **DB 500MB/프로젝트, Storage 1GB, 월 비캐시 5GB·캐시 5GB**를 제공합니다. 두 전송량은 [각각 관리](https://supabase.com/docs/guides/platform/manage-your-usage/egress)합니다. Free는 자동 백업이 포함되지 않으며, 1주 비활성 시 일시 중지될 수 있습니다. [공식 백업 안내](https://supabase.com/docs/guides/platform/backups)에 따라 정기 덤프·별도 백업을 계획합니다. 한도는 실제 구축 시 다시 확인합니다.

### 데이터베이스: 기능 전체 200MB 이하

아래는 **추정 예산이며 실제 DB 측정 결과가 아닙니다.** MB는 1,000,000바이트, KiB는 1,024바이트입니다.

| 영역 | 최대 행 수 × 보수적 행 예산 | 예산 |
|---|---:|---:|
| 공지 | 2,000 × 4KiB | 8.192MB |
| 일정 | 600 × 2KiB | 1.229MB |
| 관계 | 4,000 × 512B | 2.048MB |
| 메타 판본 | 8,000 × 2KiB | 16.384MB |
| 검수·실행·정책 | 6,000 × 1KiB | 6.144MB |
| **테이블 합계** | | **약 34MB** |
| 인덱스 | 테이블과 같은 크기로 예약 | 34MB |
| 갱신·삭제 지연·작업 여유 | | 32MB |
| 시스템·기타 점유 여유 | | 100MB |
| **총 운영 상한** | | **약 200MB** |

[공식 DB 크기 안내](https://supabase.com/docs/guides/platform/database-size)는 기본 프로젝트의 점유 및 인덱스·갱신 후 공간을 따로 고려하도록 설명합니다. 이 계획은 500MB를 수집 목표로 삼지 않고 **300MB 여유**를 남깁니다. 기존 공통 용량 기준보다 이 기능의 200MB 예산을 먼저 적용합니다.

- **160MB:** 증가 원인·인덱스·보존 상태 점검.
- **200MB 도달 또는 다음 반입으로 초과 예상:** 신규 반입 중단. 유료 전환·상한 확대 자동 실행 없음.
- 행 길이·전체 바이트를 검증하고, SQL의 `octet_length` 등으로 문자열 크기도 제한합니다. 무제한 JSONB·본문 색인·벡터는 만들지 않습니다.
- 최초 검수 샘플과 최대 크기 합성 데이터로 테이블별 `pg_total_relation_size`, DB 전체 `pg_database_size`, 인덱스·TOAST·갱신 후 크기를 실측합니다. 추정치를 넘으면 행 수·필드·색인을 줄여 다시 검증합니다.

**수행한 제한적 측정:** 메모리에서 한국어 제목 160자와 긴 URL을 가진 합성 공지 2,000건을 JSON으로 직렬화한 결과는 **2,506,031바이트(약 2.51MB)**였습니다. 실제 학교자료·Postgres·Supabase·인덱스 크기를 측정한 결과가 아닙니다. 반복 문자열의 높은 압축률은 용량 근거로 사용하지 않았습니다.

### Storage·전송·복구

**검수된 정적 공개판 우선**을 유지합니다. Supabase는 메타데이터·운영 기록의 원장으로 사용하고, 학생마다 DB 전체 JSON을 다시 내려받지 않습니다. 현재 없는 정적 어댑터·배포 경로는 #65에서 구현합니다.

| 항목 | 내부 목표와 산정 예시 |
|---|---|
| 공개판 | 전체 최대 **4MB**, 화면에 필요한 기간·페이지별로 나누어 읽음 |
| Storage | **128MB 이하**. 공개판 4개 × 4MB + 암호화 덤프 4개 × 25MB = **116MB** 예산 |
| 정기 내보내기 | 4MB × 31회 = **124MB/월** |
| 주간 덤프 | 25MB × 4회 = **100MB/월** |
| Supabase 전송 | 운영·검증 여유를 포함해 **512MB/월 목표**. 조직의 다른 프로젝트 사용량도 합산 확인 |

이는 정해진 운영 작업의 **추정치**입니다. 실제 덤프·공개판 크기와 전송량을 측정하며, 무제한 사용자 트래픽을 보장하지 않습니다. 정적 호스팅의 전송 제한은 별도로 확인합니다. 이 기능을 위해 Auth·Realtime·Edge Functions·임베딩을 추가하지 않습니다.

같은 프로젝트 안의 덤프만으로 복구를 보장하지 않습니다. 별도 암호화 백업과 복구 시험을 유지하고, 복구 때 정책판본·철회 원장을 재검사합니다. 학교 메타데이터를 Git 이력에 영구 축적하지 않습니다. 공개판·이전 배포·캐시·복구 경로의 철회는 #126의 검증을 통과해야 합니다.
